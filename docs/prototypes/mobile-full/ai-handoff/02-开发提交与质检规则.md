# 开发提交与质检规则

## 开发AI每批提交模板
- 批次ID、覆盖任务/视图ID；当前分支/提交SHA（脏工作区附patch或文件hash，不强行提交他人改动）。
- 实现内容；变更文件；API路径/方法/字段；表/迁移及旧Web兼容说明。
- 真实闭环：身份与组织（脱敏）→操作→请求→数据库记录ID/字段→独立读回→重新进入结果；不能暴露密码/token。
- 隔离守卫：服务端口、jar/schema确认方式，fixture命名与清理范围。中文业务名称，不造真实用户数据。
- 红测失败原因与绿测命令、退出码、准确数量、日志路径。列出跳过/失败，不隐藏。
- 原型对照：原图ID、当前候选/基础库/机型视口、原生截图绝对路径；正常/非空/空/错误/长名/无权情况。
- 分页：首屏/下一页/去重/失败同页/忙时reset/组织切换/重复空页/详情禁触底的证据。
- Web兼容、已知差异、未完成项、风险、回退步骤；下一批建议。
- 自检结论只写“待Codex验收”，不得自行签收。

## Codex质检流程
1. 审查真实diff与测试是否弱化；核实未改无关文件/放宽权限。
2. 检查需求/原图映射和数据契约，排除假接口、硬编码、只前端维护。
3. 独立执行针对性回归，核查入库与读回、权限负向、组织隔离、并发与失败恢复。
4. 对同一候选检查微信原生交互与截图；构建通过不等于视觉通过。
5. 输出问题单和建议方案，修复后复验；只给有证据的门打钩。

## 问题单模板
编号/严重级别/任务与视图/复现前提及步骤/实际与预期/代码定位/证据路径/根因/建议最小修复/需补测试/验收状态。
P0：泄密、真实数据破坏、权限越界等，立即停止相关部署。
P1：核心流程不可用、错误入库、跨组织污染、必需功能缺失。
P2：原型明显不符、布局遮挡、非核心交互或错误恢复缺陷。
P3：轻微间距、文案、图标一致性。
P0/P1未关不交付；用户要求1:1，P2视觉差异也不能静默接受。
