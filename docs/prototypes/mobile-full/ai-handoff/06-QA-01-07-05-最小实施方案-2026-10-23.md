# QA-01 方案：07-05 关联学校培训申请最小实施方案（待Codex确认）

日期：2026-10-23。提交人：开发AI。本文为方案待确认，未实施任何代码/迁移。

## 1. 原图与现状差异（已核实）

- 原图 07-05（reference/07-05.png）：
  - 标题"关联学校培训申请"；绿色提示卡"仅可申请加入当前就读学校或其开设的官方培训项目"
  - 所在学校下拉（阳光小学）；申请类型 radio（学校官方培训课程 / 校内社团活动）
  - 选择培训项目（2024年春季·科学探究兴趣班 >）；申请理由 textarea 0/200；底部"提交申请"按钮
- 现状实现（native-78/07-05.png）：机构入学申请管理（申请记录 header + 家庭 picker + 申请记录/填写邀请码双按钮 + 待审核 filter + 空态）
- 结论：语义不同——实现为"邀请码加入机构班级"（班级入学），原型为"参加培训项目申请"（类型/项目/理由）。不可用现有页面同名替代，也不扩展整套培训平台。

## 2. 申请对象、申请人、审核人

| 角色 | 说明 |
|---|---|
| 申请对象 | 当前就读学校的官方培训项目/校内社团活动（项目数据源见第 5 节待确认项） |
| 申请人 | 家长（家庭组织 PARENT/PARENT_ADMIN），为名下在读孩子（edu_student，且在该学校有 ACTIVE 班级关系）申请 |
| 审核人 | 学校/机构负责人或管理员（ORG_ADMIN 或持 STUDENT_ENROLLMENT_REVIEW 权限者，按机构范围） |

## 3. 状态流转、权限及组织范围

- 状态流转：PENDING → APPROVED / REJECTED（对齐现有 edu_institution_enrollment_request CHECK 三态，不新增状态）。
- 权限：
  - 家长 MINIAPP 提交：STUDENT_ENROLLMENT_REQUEST_CREATE（V108 已建 BUTTON 权限，client_type='WEB'；需按 PARENT_RELATIONSHIP 修复先例，删 client 字段或补 MINIAPP 可用性种子，并补 PARENT/PARENT_ADMIN 角色关联）
  - 审核：复用 STUDENT_ENROLLMENT_REVIEW（机构侧 Web 已有能力，MINIAPP 审核不在本视图范围）
- 组织范围：仅当前在读学校（孩子 ACTIVE 班级所属学校/校区）；培训项目候选按组织树排序；跨学校/机构不可见（对齐基线"学员关系、教师班级不得跨学校或机构"）。

## 4. 现有接口可复用 / 新增接口 / 持久化字段

- 可复用：
  - 审核链与 InstitutionEnrollmentService.review 同构（approve/reject + reviewed_by/at + review_reason）
  - 列表过滤（institutionOrganizationId / status 维度已存在）
  - V108 权限目录种子模式（sys_permission/sys_menu/sys_role_permission）
- 新增接口（最小，均挂 /api/v1/institution-enrollment）：
  1. `GET /training-programs?institutionOrganizationId=` —— 列出该校可申请的培训项目（数据源待确认，见第 5 节）
  2. `POST /training-requests` —— body: studentUserId、familyOrganizationId、institutionOrganizationId、programOrganizationId、requestType（OFFICIAL_COURSE / CLUB_ACTIVITY）、reason（≤200）
  3. `GET /training-requests?status=&familyOrganizationId=` —— 家长查看本家庭申请与状态
  4. 审核复用：`POST /training-requests/{id}/approve|reject`（机构侧，Web 兼容）
- 持久化字段（新建独立表 edu_institution_training_request，不污染入学表）：
  - id BIGINT PK；student_id → edu_student；family_organization_id / institution_organization_id / program_organization_id → sys_organization；request_type VARCHAR(16) CHECK IN('OFFICIAL_COURSE','CLUB_ACTIVITY')；reason VARCHAR(200)；status CHECK IN('PENDING','APPROVED','REJECTED')；requested_by → sys_user；reviewed_by/at；review_reason VARCHAR(200)；created_at；索引（family+status、institution+status、student+status）

## 5. 与班级入学、培训机构入驻的区别

| 场景 | 入口 | 目标 | 审核后动作 |
|---|---|---|---|
| 班级入学（04-07/04-08） | 邀请码 | 成为机构班级成员（学籍关系） | 落 student_organization ACTIVE |
| 培训项目申请（07-05 原型） | 项目列表 | 参加官方培训课/社团活动 | **不自动变更学籍班级**，仅记录申请结果 |
| 培训机构入驻申请（01-08） | 渠道入驻 | 机构本身入驻平台 | 机构资质审核 |

## 6. 待 Codex 确认的语义冲突（不自行决策）

1. **培训项目数据源**：现有组织树"课程班"（CLASS 类型节点 + V128 课程分类元数据）是否直接作为"培训项目"候选？推荐：是（不新建 training_program 实体，最小闭环；课程分类即申请类型映射：课程班=官方培训课程，社团类暂以课程分类区分）。
2. **审核通过后的关系落地**：推荐仅记录申请结果与审核结论，成员/参与关系由机构侧班级管理另行操作（避免自动改学籍）；是否接受？
3. **申请类型枚举**：OFFICIAL_COURSE / CLUB_ACTIVITY 两值是否固定（原图仅两 radio）？
4. **页面形态**：原图为独立表单页；现实现为入学管理页。推荐 07-05 页按原图重做表单（提示卡+学校+类型 radio+项目 picker+理由+提交），入学申请记录入口保留在现有页不冲突。是否接受？

## 7. 不做的事

- 不新建整套培训平台（报名、缴费、考勤、结课）——本项目仅申请与审核。
- 不动班级入学邀请码链路（04-07/04-08 已通过项）。
- 不伪造项目数据：培训项目列表来自隔离库真实课程班，无真实数据时如实空态。
