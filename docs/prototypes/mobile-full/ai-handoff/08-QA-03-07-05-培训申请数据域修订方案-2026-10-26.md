# QA-03 方案：07-05 关联学校培训申请数据域修订方案（待Codex确认，修订QA-01）

日期：2026-10-26。提交人：开发AI。本文修订 06-QA-01 方案，吸收 N04 质检意见；仅方案，未实施任何代码/迁移。

## 1. 修订背景（对齐 N04）

QA-01 的缺口：候选数据源"课程班即培训项目"会把任意 CLASS 自动当作可报名项目；"审核不产生参与关系"未经需求确认。本修订补齐最小闭环定义，明确以下不变式：

- 任意 CLASS 不自动成为可报名项目，须机构显式登记；
- 审核通过后可查询参与关系，但不改变孩子主班级（不动 edu_student_organization 班级关系）；
- 邀请码入学链路（V108 edu_institution_enrollment_request）保持不变。

## 2. 数据域最小闭环（新建三表，不动现有表语义）

### 2.1 可报名项目登记（数据源，新增）

`org_training_program_registration`：机构把某个课程班/活动节点显式登记为"可报名培训项目"。

| 列 | 说明 |
|---|---|
| program_organization_id BIGINT PK | → sys_organization（课程班/社团 CLASS 类节点） |
| institution_organization_id BIGINT NOT NULL | 所属机构（申请范围校验与列表过滤用） |
| program_type VARCHAR(16) NOT NULL | CHECK IN('OFFICIAL_COURSE','CLUB_ACTIVITY')，对应原图两个 radio |
| enrollable VARCHAR(16) NOT NULL | CHECK IN('ENABLED','DISABLED')，默认 ENABLED |
| updated_by BIGINT NULL / updated_at TIMESTAMP | 操作留痕 |

索引（institution_organization_id, enrollable, program_type）。未登记或 DISABLED 的 CLASS 不出现在申请候选，无候选时页面如实空态，不伪造。

### 2.2 培训申请（独立类型与状态，新增）

`edu_institution_training_request`：家长为孩子提交的培训/活动申请，独立于入学请求表。

| 列 | 说明 |
|---|---|
| id BIGINT PK | 雪花 |
| student_id BIGINT NOT NULL | → edu_student（须在该机构有 ACTIVE 班级在读关系） |
| family_organization_id BIGINT NOT NULL | → sys_organization（申请人家庭） |
| institution_organization_id BIGINT NOT NULL | 申请机构 = 孩子 ACTIVE 班级所属机构 |
| program_organization_id BIGINT NOT NULL | 可报名项目（须同机构且 enrollable=ENABLED） |
| request_type VARCHAR(16) NOT NULL | CHECK IN('OFFICIAL_COURSE','CLUB_ACTIVITY') |
| reason VARCHAR(200) | 申请理由，≤200 |
| status VARCHAR(16) NOT NULL | CHECK IN('PENDING','APPROVED','REJECTED','WITHDRAWN') |
| pending_guard BIGINT NULL | PENDING 时置 1，终态置 NULL，配合唯一索引防重复 |
| requested_by BIGINT NOT NULL | → sys_user（家长） |
| reviewed_by BIGINT NULL / reviewed_at TIMESTAMP NULL / review_reason VARCHAR(200) NULL | 审核留痕 |
| created_at TIMESTAMP | |

唯一索引 (student_id, program_organization_id, pending_guard)（MySQL 多 NULL 允许重复申请新纪录）；索引（family+status、institution+status、student+status）。

- 重复防护：同孩子同项目存在 PENDING → 拒绝（409，提示"已有待审核申请"）；终态后允许重新申请。
- 撤回：仅 PENDING 可由申请人本人或同家庭 PARENT_ADMIN 撤回 → WITHDRAWN（记录保留，不删除）；撤回后可重新申请。

### 2.3 审核通过后的参与关系（新增）

`edu_training_participation`：审核通过时同事务落一条参与关系，家长/机构可查询；不写入 edu_student_organization，孩子主班级不变。

| 列 | 说明 |
|---|---|
| id BIGINT PK | 雪花 |
| training_request_id BIGINT NOT NULL UNIQUE | 一次申请最多一条参与关系 |
| student_id / program_organization_id / institution_organization_id BIGINT NOT NULL | 快照 |
| status VARCHAR(16) NOT NULL | CHECK IN('ACTIVE','LEFT') |
| joined_at TIMESTAMP NOT NULL / left_at TIMESTAMP NULL | 结课/退出留痕 |

索引（student_id, status）、（program_organization_id, status）。

## 3. 状态表与流转

| 状态 | 触发 | 可流转 |
|---|---|---|
| PENDING | 家长提交 | 撤回→WITHDRAWN；审核→APPROVED/REJECTED |
| APPROVED | 机构审核通过 | 同事务落参与关系 ACTIVE |
| REJECTED | 机构驳回 | 终态（可重新申请新纪录） |
| WITHDRAWN | 家长撤回 | 终态（可重新申请新纪录） |

审核幂等：非 PENDING 再审核 → 409（重复审核被拒，不回退参与关系）。

## 4. 接口（挂 /api/v1/institution-enrollment 下，与现有控制器同域）

1. `GET /api/v1/institution-enrollment/training-programs?institutionOrganizationId=&studentId=` —— 返回该机构内 enrollable=ENABLED 的项目（含类型、名称、课程分类元数据 org_course_category_metadata 的 description/stage）；studentId 用于校验该孩子在该机构有 ACTIVE 班级在读关系，无则 403 空列表。
2. `POST /api/v1/institution-enrollment/training-requests` —— body: studentId、institutionOrganizationId、programOrganizationId、requestType、reason(≤200)。服务端再校验：孩子在读范围、项目同机构且 ENABLED、无 PENDING 重复。
3. `GET /api/v1/institution-enrollment/training-requests?status=&familyOrganizationId=&studentId=` —— 家长查本家庭申请与状态。
4. `POST /api/v1/institution-enrollment/training-requests/{id}/withdraw` —— 家长撤回 PENDING。
5. `POST /api/v1/institution-enrollment/training-requests/{id}/approve` / `.../reject` —— 机构审核（body: reviewReason；reject 必填）。approve 同事务落参与关系。
6. `GET /api/v1/institution-enrollment/training-participations?studentId=` —— 家长/机构查询参与关系（审核结果可见）。

## 5. 权限（菜单按钮码，不用角色名兜底）

- 新按钮码 `STUDENT_TRAINING_REQUEST_CREATE`（BUTTON；client MINIAPP+WEB 可用）。按 V136 先例：不设 client 限制或补 MINIAPP 可用性；为 PARENT/PARENT_ADMIN 内置角色补种 sys_role_permission（只增不删幂等）。
- 新按钮码 `STUDENT_TRAINING_REQUEST_REVIEW`（BUTTON；机构侧 WEB/MINIAPP 均可）。按 V108 先例：从持 STUDENT_ENROLLMENT_REVIEW 的角色/用户镜像补种（只增不删）。
- 审核范围：仅申请中 institution_organization_id 的本机构管理员；跨机构 403。
- 家长范围：仅本家庭（family_organization_id 归属校验），不能查其他家庭申请。

## 7. 范围负例（T07 实施时逐条落地验证）

1. 未登记/已 DISABLED 的 CLASS 不出现在候选列表；
2. 孩子不在该机构 ACTIVE 在读 → 项目列表 403/空、提交被拒；
3. 跨机构提交（program 属于别校）→ 400/403；
4. 同孩子同项目 PENDING 重复提交 → 409；
5. 非申请人本人/非本家庭撤回 → 403；
6. 非本机构管理员审核 → 403；非 PENDING 重复审核 → 409；
7. 通过后 edu_student_organization 班级关系不变，参与关系可独立查询；
8. 权限负例：无 CREATE 码的家长 403；无 REVIEW 码的机构成员 403。

## 2026-10-27 Codex 强制实施约束（覆盖上文有歧义的示例）

1. 增加参与关系 `(student_id, program_organization_id, active_guard)` 唯一约束：ACTIVE 的 guard=1，LEFT 为 NULL。申请时已有 ACTIVE 必须拒绝，审批并发也由数据库唯一约束兜底；请求状态 CAS、参与插入、审核记录同事务，重复审核不得重复插入。
2. 同一孩子在不同机构/项目的参与完全独立，不能覆盖 edu_student 的学校、班级或其他全局字段。
3. 培训项目须经显式登记，补最小登记/启停接口与管理入口并挂现有权限体系。任意班级不自动成为可报名项目。服务端验证其机构层级、启用及可报名状态。
4. 列表/详情/提交/撤回每次核验有效监护关系、申请人边界；审核须动作权限+目标机构范围，无角色名特权。停用项目、失效关系、跨校、重复参与、并发审核均补隔离 API/SQL 负例。
5. 此为已获用户授权的修订约束，不新增业务范围；T07 可据此实施，T05-Q 等独立复验后再勾。
