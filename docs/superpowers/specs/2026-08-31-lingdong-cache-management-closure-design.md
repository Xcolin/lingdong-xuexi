# 灵动伴随缓存管理闭环设计

## 1. 目标与范围

本专项复用 V11 已有缓存领域、字典缓存处理器、操作台账和系统任务审批能力，补齐 Web 管理所需的功能开关、动态权限、REST/OpenAPI、操作历史、管理员执行和审核员审批。uni-app 不增加平台缓存管理页面、路由或接口调用。

本专项不虚构尚未实现的缓存。字典缓存可以真实刷新和清除；用户会话清除会撤销全部活动设备会话；未注册处理器的权限、组织、功能开关和统计缓存执行后必须记录失败原因。全量清除只清理 Spring `CacheManager` 当前已注册缓存。

## 2. 权限与角色边界

- `CACHE_READ`：查看缓存域、操作历史和本人可见的处理结果。
- `CACHE_MANAGE`：执行非全量、非会话缓存的直接刷新或清除；可授予自定义运维角色。
- `CACHE_REVIEW`：查看并审批高风险缓存任务；V52 仅授予系统审核员。
- 全量清除和用户会话清除只能由活动 `SYS_ADMIN` 提交，并只能由活动 `SYS_AUDITOR` 通过或驳回。
- 功能开关 `CACHE_MANAGEMENT` 停用后，Web 菜单和直达路由隐藏，所有缓存管理接口拒绝访问。

前端权限只控制可见性。后端控制器通过 `@RequirePermission` 检查动态权限，应用服务继续复核高风险操作的固定角色边界。

## 3. 接口与流程

- `GET /api/v1/cache-management/operations`：按创建时间倒序查询最近 200 条操作台账。
- `POST /api/v1/cache-management/operations`：执行普通缓存操作并返回成功或失败台账。
- `POST /api/v1/cache-management/review-submissions`：系统管理员创建高风险任务并立即提交审核。
- `GET /api/v1/cache-management/review-queue`：系统审核员查询待审核的缓存任务。
- `POST /api/v1/cache-management/review-queue/{taskId}/approve`：审批通过后执行；仅执行成功才将系统任务置为生效。
- `POST /api/v1/cache-management/review-queue/{taskId}/reject`：填写必填意见并驳回，缓存台账置为 `REJECTED`，不执行缓存操作。

所有雪花标识按字符串返回。直接操作失败仍返回业务台账，其 `status=FAILED`，不伪装为接口成功结果。参数错误、越权、功能停用和不存在的任务继续使用统一异常响应。

## 4. Web 交互

页面路由为 `/cache-management`。具备 `CACHE_READ` 时显示入口；具备 `CACHE_MANAGE` 时显示普通操作和高风险提交表单；具备 `CACHE_REVIEW` 时显示待审核列表以及通过、驳回操作。自定义运维角色没有审核按钮，系统审核员没有直接执行或提交按钮。

普通操作下拉只显示当前有真实处理器的数据字典缓存。高风险提交必须勾选固定确认项，用户会话清除批准后包括审核员当前会话在内的全部旧会话立即失效。驳回必须填写意见。历史表格显示缓存域、操作类型、状态、影响说明、申请人、执行人、失败原因和时间；失败原因仅展示服务端已脱敏文本。

## 5. 验收边界

验收覆盖 V1-V52 连续迁移、19 位种子、三类动态权限、功能停用、普通执行、全量清除、用户会话全局撤销、高风险提交、系统审核员通过和驳回、OpenAPI、Web 权限态与错误反馈。执行后端与 Web 全量测试和构建、uni-app 类型检查与双目标构建，并扫描敏感信息、定位能力和补丁格式；桌面和 390px 窄屏执行视觉检查。远程 Redis、MySQL、共享测试、预生产、生产和业务 UAT 不计入本地完成。
