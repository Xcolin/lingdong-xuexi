# 灵动学习业务需求基线重构设计

**适用文档**：`灵动学习-业务需求说明书-V1.0.md`

**目标**：将现有业务需求说明书重构为可直接用于产品原型、研发拆分、测试设计和验收评审的唯一业务基线。

## 1. 评估结论

现有说明书已覆盖组织权限、系统配置、账号、任务、积分、机构协同、统计和技术约束等主模块，能够表达产品范围；但不能直接作为完整开发基线，原因如下：

1. 原始素材中关于登录与绑定、任务编辑和顺延、积分纠错、消息通知、离线同步、设备会话、考勤异常、数据导出和维护模式的细则未被完整吸收。
2. 多个跨模块规则只出现一次或仅以原则表达，例如功能开关对存量流程的处理、数据删除与留存、系统审核与普通业务审核的边界、导出审批与脱敏的关系。
3. 当前功能清单、流程图、状态表、字段表和权限表之间未逐项建立可追溯关系；开发人员无法从一个功能点直接确定其入口、状态、数据范围、通知、审计和验收结果。
4. 原始素材与最新确认口径存在历史冲突，例如角色名称、教师终端限制、一期二期划分和多终端范围；需要统一裁决，而非同时保留。

## 2. 规则优先级与范围裁决

业务规则按以下优先级解释：

1. 本轮已确认的业务口径：六类角色、系统审核员仅审核系统管理员高风险系统任务、机构与家庭双主体、RBAC与区域学校组织树、功能停用后隐藏、Web和小程序独立应用且高频操作双端覆盖、不做一期二期划分、既定技术选型与系统配置模块范围。
2. 现有《灵动学习-业务需求说明书-V1.0》中的有效规则。
3. 《灵动学习-需求原始素材汇总V1.0》中的不冲突规则。

因此，重构后的说明书使用“系统管理员”替代“平台超级管理员”；不保留“教师仅移动端”“Web无教师入口”“一期/二期”等历史口径；不把原始素材中未确认的额外终端单独列为本次建设应用。

## 3. 重构方式

采用一个完整业务需求文档，不拆分为多份相互引用的需求文档。每个模块都采用同一描述结构：

1. 模块定位、业务对象与角色。
2. 功能清单：为每个功能分配业务编号，并明确功能名称、使用角色、端应用、输入、处理结果和优先级。
3. 功能流程：主流程、异常流程、跨模块触发关系。
4. 状态和时序：状态定义、流转条件、不可逆规则、超时和定时任务。
5. 业务规则：字段、校验、权限、数据隔离、日志、消息、功能开关、历史数据处理。
6. 关联关系：上游来源、下游影响、依赖的公共能力和验收要点。

跨模块的通用规则只定义一次，并在各功能中通过“适用规则”明确引用，避免同一规则在多个模块中发生歧义。

## 4. 目标模块结构

1. 项目概述、范围、名词和角色矩阵。
2. 应用边界和全域业务总流程。
3. 全局公共能力：会话与设备、消息、附件、字典、导入导出、搜索分页、操作日志、离线同步、维护模式、功能开关、数据隔离和数据生命周期。
4. 组织、用户与RBAC权限管理。
5. 系统配置、系统审核、接口服务和系统运维。
6. 账号、认证、学生账号和家庭关系管理。
7. 家庭、机构、教师学习任务管理。
8. 学生执行、情绪暂停、难题搁置和亲子答疑预约。
9. 积分、奖励兑换和成长复盘。
10. 学校机构、班级、教师、学员、考勤和异常报备。
11. 统计看板、报表、台账与数据导出。
12. 页面清单、端应用权限矩阵、字段和交互规范。
13. 技术约束、安全隐私、合规与验收追溯。

## 5. 关键实施决策

### 5.1 Web 与小程序边界

Web端承载全部复杂配置、批量处理、全量台账、复杂统计、组织权限管理、接口服务管理和系统运维。小程序端承载高频、单笔、待办型操作及摘要查看。

系统管理员的小程序端可查看系统待办、发起简化系统任务、查看审批结果和公告；系统审核员的小程序端可查看、审批或驳回待审系统任务。涉及组织、权限、字典、接口、模板、缓存和复杂统计的完整配置与查询只在Web端提供。

家长、教师、机构管理员的高频业务操作在两端保持同一业务结果；学生以小程序端为主要执行端。两端不共用页面工程，但必须共享同一后端业务规则、状态定义和权限校验结果。

### 5.2 功能开关

每个受控功能必须定义：开关范围、默认状态、适用角色和组织、停用时入口处理、接口拦截、存量待办处理、历史数据可见性、恢复后的生效范围、变更日志和是否属于高风险系统任务。

功能开关优先于RBAC。关闭后前端隐藏且后端拒绝新操作；已产生数据保留。存量任务不得用一个笼统规则处理，应在对应业务模块明确“继续、转交、自动驳回、暂停或只读”的唯一结果。

地理考勤与学生轨迹属于独立受控功能，默认停用。停用时，Web端和小程序端均不展示围栏、考勤、轨迹和位置授权入口；后端拒绝位置采集、地图调用、自动签到签退和轨迹生成请求；不生成新的位置数据和考勤数据。已有历史数据仍按既定权限和留存期限处理。

面向个人主体、工具类目首次发布的小程序构建包不纳入定位采集、轨迹记录和地图调用能力，不能仅依赖运行时开关隐藏页面。未来在满足业务主体、平台审核和家长授权条件后，才单独构建并发布包含该能力的版本；启用全局地理考勤功能属于高风险系统任务，需由系统管理员发起并经系统审核员审批。

### 5.3 权限与系统审核

RBAC的最终权限结果由功能开关、显式禁止权限、角色权限、用户补充权限、数据范围和组织范围共同计算。用户补充权限只能补充功能操作，不得扩大已有组织范围和数据范围；明确禁止优先于所有允许。

系统审核员只处理系统管理员发起的高风险系统任务。学习任务审核、积分审核、兑换审批、打卡审核和考勤审批属于业务流程，必须由其所属业务角色处理，不进入系统审核队列。

### 5.4 任务、积分和家庭机构关系

家庭、机构和教师任务是不同来源的任务实例，统一由学生执行，统一进入一个累计总积分账户和一个可用积分账户；任务来源、审核人、来源组织和积分台账必须可追溯。

机构和家庭可独立存在。机构关联家长只建立学生维度的协同关系，不使机构取得家庭私有任务、家庭奖励、家庭积分配置和家庭复盘的查看或操作权限。

### 5.5 数据生命周期

账户注销与历史业务留存按“停止登录、关系解除、身份匿名化、法定或审计所需记录保留”的原则描述，避免“永久留存”和“完全删除”同时成立。学生轨迹保留180天；操作日志热存储180天后冷归档；其他业务记录的保留、删除、归档与附件物理删除条件必须在数据生命周期表中逐项明确。

### 5.6 数据库迭代

后端数据库结构、初始化基础数据和受控数据修正必须使用Flyway进行版本化迁移。研发、测试、预生产和生产环境均以迁移脚本版本为唯一依据，禁止将手工改库作为常规发布方式。每个迁移版本需具有唯一版本号、明确变更说明和可验证结果；涉及数据修复、字典初始化、权限初始化或历史数据回填时，必须保留可追溯记录，并纳入发布验证。

## 6. 重构后的验收标准

完成后，任一功能点均可回答以下问题：

1. 哪些角色可在Web或小程序使用，入口是否受功能开关和RBAC控制。
2. 输入什么数据，字段如何校验，产生或修改哪些业务对象。
3. 主流程、异常流程、超时流程和状态变化是什么。
4. 影响哪些任务、积分、家庭关系、机构统计、消息和日志。
5. 谁能查看、编辑、审核、导出或处理历史数据。
6. 功能关闭、账号停用、组织停用、审核人失效或解绑时如何处理。
7. 如何从台账、日志、消息和统计中验收该功能执行结果。
8. 数据库版本迁移是否通过Flyway脚本执行，且迁移结果可验证、可追溯。

## 7. 本次不纳入的内容

本次只完善业务需求基线，不产出数据库表结构、接口字段协议、页面原型、代码、部署方案或第三方厂商选型；但会列出这些后续设计所必须遵守的业务约束。
