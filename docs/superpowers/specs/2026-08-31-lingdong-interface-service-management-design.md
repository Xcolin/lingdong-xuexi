# 灵动学习接口服务管理闭环设计

## 1. 目标与范围

本专项在 V12 接口服务登记、变更提案和调用结果台账基础上，完成 Web 端可验收的接口服务管理闭环。系统管理员提交接口登记、重新启用、停用和授权范围变更，系统审核员审批或驳回；服务元数据只在审批通过并执行成功后生效。

本专项不保存接口地址、密钥、访问令牌、签名原文、请求体或响应体，不提供人工伪造调用日志的 REST 接口。调用方鉴权、签名、限流、幂等、熔断和具体供应商适配继续归 WBS-09，在协议与供应商明确后实施。

## 2. 方案选择

采用“元数据管理闭环”方案：复用 V12 三张表和系统任务状态机，V53 只增加功能开关、动态权限及内置角色授权；后端补查询、重新启用、驳回和 REST/OpenAPI，Web 增加独立管理页面。

未采用一次性实现完整接口网关的方案，因为当前没有调用协议、签名算法、限流阈值、幂等键和熔断参数，提前固化会新增原始需求之外的内容。未采用先重构通用系统任务执行器的方案，因为本专项已有稳定领域服务，抽象通用执行器会扩大改动面。

## 3. 权限与职责

1. `INTERFACE_SERVICE_READ`：查看生效服务、变更记录、审核队列和调用结果台账。
2. `INTERFACE_SERVICE_MANAGE`：进入提交登记、启停和授权范围变更的操作界面。
3. `INTERFACE_SERVICE_REVIEW`：审批或驳回接口服务系统任务。
4. 系统管理员必须同时具备 `INTERFACE_SERVICE_MANAGE` 才能提交，但固定角色约束仍要求提交人是 `SYS_ADMIN`。
5. 系统审核员必须同时具备 `INTERFACE_SERVICE_REVIEW` 才能审核，系统任务服务仍固定要求审核人是 `SYS_AUDITOR`。
6. 系统审核员不能提交，系统管理员不能审核；动态权限不能突破固定职责分离。
7. 功能开关 `INTERFACE_SERVICE_MANAGEMENT` 停用后，Web 菜单、直达页面和操作按钮全部不可见，后端所有管理查询与写接口均拒绝。

## 4. 状态与流程

### 4.1 登记

系统管理员填写服务名称、方向、用途、调用方、授权范围、责任人、任务标题和影响说明。后端在同一事务内创建变更快照和系统任务草稿，随后提交为待审核；此时不创建生效服务。审核通过后创建 `ENABLED` 服务并将任务标记为已生效，驳回后服务保持不存在。

### 4.2 启停

启用和停用都创建不可变变更快照并提交审核。只有当前为 `DISABLED` 的服务可提交启用，只有当前为 `ENABLED` 的服务可提交停用。审批通过后执行条件更新，避免并发旧请求覆盖新状态；驳回不改变服务。

### 4.3 授权范围

授权范围支持 `GLOBAL`、`REGION`、`SCHOOL`、`INSTITUTION` 和 `SPECIFIED_CALLER`。`GLOBAL` 不允许范围值，其他范围必须提供不超过 128 字符的范围值。变更审批通过前继续使用原授权范围。

### 4.4 调用结果台账

管理页面只读展示内部适配器已写入的调用结果，包括服务、调用方、结果、脱敏异常摘要、追踪标识和发生时间。停用服务不能新增调用记录；台账不包含凭证或完整报文。

## 5. 后端接口

1. `GET /api/v1/interface-services`：按服务名称、调用方、状态、用途和责任人筛选生效服务。
2. `GET /api/v1/interface-services/changes`：查询最近变更及系统任务状态。
3. `GET /api/v1/interface-services/call-logs`：查询最近调用结果，可按服务和结果筛选。
4. `GET /api/v1/interface-services/review-queue`：查询接口服务待审核任务。
5. `POST /api/v1/interface-services/registration-submissions`：创建登记快照并提交审核。
6. `POST /api/v1/interface-services/{serviceId}/enable-submissions`：提交重新启用任务。
7. `POST /api/v1/interface-services/{serviceId}/disable-submissions`：提交停用任务。
8. `POST /api/v1/interface-services/{serviceId}/authorization-submissions`：提交授权范围变更任务。
9. `POST /api/v1/interface-services/review-tasks/{taskId}/approve`：审批并执行变更。
10. `POST /api/v1/interface-services/review-tasks/{taskId}/reject`：驳回变更。

所有雪花标识在 JSON 中使用字符串，查询数量由后端限制在 1 至 200 条。错误响应沿用统一异常处理，不回传底层 SQL、凭证或完整第三方异常。

## 6. Web 交互

Web 独立路由 `/interface-services`，不在 uni-app 增加页面、API 或路由。页面包含“服务登记”“变更审核”“调用台账”三个页签：

1. 服务登记页签提供筛选、服务表格、登记按钮、启停按钮和授权范围变更按钮。
2. 变更审核页签展示待审核任务和最近变更；只有审核权限显示通过、驳回操作。
3. 调用台账页签展示只读结果，宽表在内部滚动，页面本身不得横向溢出。
4. 缺少维护权限时页面保持只读；缺少审核权限时不显示审核按钮。
5. 提交、启停、授权调整和审批均使用确认反馈；请求失败保留已填写表单并展示后端错误。

## 7. 数据库与迁移

V53 不新增业务表，也不修改 V12 历史迁移。迁移只新增一个功能开关、三项权限和四条内置角色授权，全部使用 19 位雪花数字。重新启用复用 `sys_interface_service_change.target_status`，不需要新增字段。

## 8. 验收

后端测试覆盖 V53 种子、19 位标识、查询筛选、登记、启用、停用、授权变更、审批、驳回、动态权限、固定角色、功能停用、调用台账脱敏和 OpenAPI。Web 测试覆盖管理员提交、审核员处理、只读状态、错误反馈和功能入口；完成桌面及 390px 窄屏检查。最后执行后端、Web、uni-app 全量测试与构建，并扫描敏感信息、定位能力和补丁格式。
