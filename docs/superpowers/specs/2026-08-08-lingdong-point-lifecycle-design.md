# 灵动学习 V29 积分生命周期设计

## 1. 目标与范围

V29 落地固定任务积分阶梯衰减、连续 30 天沉睡清零、清零前 3 天主家长提醒待投递、生命周期审计和积分明细透明展示。全部规则基于原始需求，不增加扣分或惩罚机制。

V29 不实现微信或站内消息实际发送，也不新增没有需求依据的活跃行为。提醒先进入可靠待投递表，后续消息模块按夜间抑制、去重和归档规则统一发送。

## 2. 当前模型缺口与处理

原始需求将“同一固定任务”定义为任务 ID 相同，复制昨日任务生成新任务 ID，不继承衰减；家庭、机构和教师来源分别计算。当前 `learn_task_assignment` 约束为一个任务 ID 对每个学生只有一条实例，因此无法出现连续 8 个自然日的同任务实例。

V29 将实例唯一约束调整为“任务 ID、学生 ID、计划日期”唯一，使同一固定任务可在不同自然日形成独立执行实例。V29 不擅自增加固定任务结束日期、重复星期或停止规则；固定任务的创建和跨日实例生成归入学习任务剩余能力专项。衰减引擎从 V29 起对所有合法的同任务跨日实例生效，复制任务因任务 ID 不同天然重新计数。

## 3. 衰减口径

1. 业务时区为 `Asia/Shanghai`，连续性按任务实例 `scheduled_date` 自然日计算，不按审核发生时间计算。
2. 同一学生、同一任务 ID、同一来源类型连续完成形成一个序列。任务 ID 已唯一确定来源，来源字段同时保存用于审计和防御性校验。
3. 第 1 至 7 个连续自然日发放 100% 基础积分；第 8 至 15 日发放 80%；第 16 日起发放 60%，最大衰减 40%。
4. 前一个有效完成日不是当前计划日的前一自然日时，当前连续天数重置为 1，发放全额积分。
5. 有效完成只认未被纠错的 `TASK_REWARD` 台账。已纠错奖励不参与连续性；同一任务重新审核后，以新奖励重新参与计算。
6. 基础积分仍为 10、20、30，因此按整数百分比计算没有舍入歧义。客户端不得提交基础积分、连续天数、比例或实发积分。
7. 每笔任务奖励固化任务 ID、基础积分、实发积分、连续天数、衰减比例和规则版本。历史台账不随规则调整重算。

## 4. 沉睡口径

1. 学生最后有效活跃时间后连续 27 天没有有效活跃时，生成一次主家长提醒待投递记录；连续 30 天没有有效活跃时清空可用积分。
2. 清零只将 `available_points` 变为 0，`total_points` 不变；追加 `DORMANCY_CLEAR` 不可变台账，`amount=0`、`available_delta=-清零前可用积分`。
3. 可用积分已经为 0 时不生成零变化积分台账，但沉睡状态仍记录本轮已检查，防止重复处理。
4. 有效活跃包括任务认领、暂停、恢复、放弃、打卡、审核导致完成、免执行、积分变化和用户主动复盘补录。自动复盘生成、登录和只读查询不计活跃。
5. `DORMANCY_CLEAR` 自身不计积分活跃，避免清零动作重置自己的计时。后续任务操作、非清零积分变化或复盘补录会建立新的活跃基线。
6. 提醒只面向处理时仍有效的主家长。没有活动主家长时保留未指定接收人的待投递事实，不向其他角色扩大通知范围。
7. 计时使用上海时区精确时间：提醒到期为最后活跃时间加 27 天，清零到期为加 30 天。批处理按当前时间处理到期记录并保持幂等。

## 5. 数据模型

### 5.1 `growth_point_decay_rule`

保存连续起始天数、衰减百分比、启停状态、生效时间和版本。V29 初始化第 8 天 20%、第 16 天 40% 两条规则；规则主键为 19 位雪花常量。

### 5.2 `growth_point_dormancy_state`

每名学生一条状态，主键复用学生雪花标识，保存最后活跃时间、提醒/清零到期时间、本轮提醒时间、本轮清零时间和乐观锁版本。活动更新使用账户或状态行锁，不能把时间回拨。

### 5.3 `growth_point_dormancy_notice`

保存学生、主家长、活跃基线、到期时间、创建时间和投递状态。学生与活跃基线唯一，批处理重试不产生重复提醒；V29 只创建 `PENDING` 记录，不记录虚假的发送成功。

### 5.4 积分台账扩展

`growth_point_ledger` 增加任务 ID、基础积分快照、衰减百分比、连续天数、衰减规则 ID 和沉睡提醒/周期 ID。任务奖励必须具备完整衰减审计字段；沉睡清零必须唯一关联对应活跃基线的提醒记录，使账号重新活跃后仍可形成新的清零周期。

## 6. 事务与并发

1. 审核通过继续锁定任务实例、打卡和积分账户，在同一事务中查询有效连续记录、选择生效规则、更新账户、写任务奖励台账并完成任务状态。
2. 同一学生的并发审核由积分账户行锁串行化；台账查询在账户锁之后执行，避免两个审核同时基于旧连续记录计算。
3. 沉睡批处理按学生 ID 游标分页。每个学生在独立事务内重新锁定状态和账户、重算最新活跃时间，再决定提醒或清零。
4. 提醒唯一约束、沉睡台账唯一关联和状态版本共同保证重复调度幂等；单个学生失败不阻断其他学生。
5. `POINT_LIFECYCLE` 功能开关关闭后不执行新衰减、提醒和清零；历史台账仍按积分查询权限可读。

## 7. 验收边界

必须覆盖第 1、7、8、15、16、40 天，中断一个自然日，复制任务新 ID，来源隔离，纠错奖励排除，并发审核，27 天提醒，30 天清零、零余额、活动重置、重复批处理、无主家长、开关停用和全部 19 位标识规则。

本地验证继续只使用 H2 MySQL 兼容模式和测试时钟，不连接远程 MySQL、Redis、微信、共享测试、预生产或生产环境。
