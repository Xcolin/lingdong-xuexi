# 灵动伴随通用组织数据范围查询设计

## 1. 目标

将现有只返回单对象布尔结果的数据范围服务扩展为可复用查询组件，统一表达全部、本区域、本学校、本班级、本人和自定义范围，并保持角色范围、用户组织关系和组织管理员范围的既有交集规则。

## 2. 范围结果

应用层输出不可变 `OrganizationDataScope`：

- `allOrganizations`：是否允许全部组织；只有活动角色的 `ALL` 可产生。
- `selfAllowed`：是否具有 `SELF` 范围，供业务对象层继续判断本人、本人孩子或本人任务。
- `rootPaths`：允许访问的组织子树根路径，经过交集计算、去重和包含关系归并。

组织查询只使用 `allOrganizations` 与 `rootPaths`；`SELF` 不自动转换为组织权限，避免把“本人”错误扩大为所在组织全部数据。

## 3. 解析规则

1. 无活动角色返回空范围；`ALL` 直接返回全部组织，同时保留是否具有 `SELF` 的事实。
2. `REGION/SCHOOL/CLASS` 使用角色授权时绑定组织作为根，且组织类型必须与范围类型一致；类型不匹配的历史异常授权不产生访问范围。
3. `CUSTOM` 使用角色配置的组织根；`SELF` 只设置本人标志。
4. 非全部范围先与用户显式组织关系取交集；用户存在组织管理员配置时，再与管理员组织根取交集。
5. 两个子树相交时保留更窄路径；同一集合中宽路径覆盖窄路径，输出稳定排序且不可修改。
6. 组织停用不改变历史查询授权事实；新业务能否操作仍由组织有效状态服务独立判断。

## 4. 查询复用

`OrganizationDataScopeService.resolve(userId)` 返回统一范围；`canAccess` 使用同一结果判断单个组织；组织 Mapper 增加按范围根路径查询的方法，供后续业务列表逐步替换重复的组织管理员子查询。全部范围查询全部组织，空或本人范围不返回组织。

## 5. 安全边界

- 用户补充功能权限不能修改组织范围结果。
- 前端不得提交根路径或可见组织集合；范围只由当前用户的数据库事实解析。
- 业务对象的本人、家长关系、教师班级和学生关系仍由对应业务服务校验，不能只依赖组织范围。
- 本专项不新增表、不创建 Flyway 空迁移，不连接远程 MySQL、Redis、共享测试、预生产或生产环境。
