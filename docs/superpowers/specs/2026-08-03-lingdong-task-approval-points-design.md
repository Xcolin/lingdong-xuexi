# 灵动学习 V24 任务审核通过与积分原子入账设计

## 1. 目标与范围

V24 在 V23 任务执行和业务审核基础上补齐“审核通过”闭环。当前审核人确认通过后，系统必须在同一数据库事务内完成打卡通过、任务完成、学生积分账户更新、积分台账写入和任务事件记录。

本里程碑只实现任务奖励积分。积分纠错、兑换、核销、休眠清零、统计报表和消息通知不进入 V24，避免在首个资金式台账事务中混入尚未稳定的状态机。

## 2. 核心规则

1. 只有 `PARENT`、`TEACHER`、`ORG_ADMIN` 中的当前审核人可以审核通过；系统审核员没有该入口。
2. 任务实例必须为 `PENDING_REVIEW`，最新打卡必须为 `SUBMITTED`。
3. 奖励数量使用任务发布时由服务端确定的基础积分，只允许 10、20、30 分。
4. 三类任务均累加到学生唯一账户的累计积分和可用积分。
5. 同一任务实例只能产生一条 `TASK_REWARD` 台账；数据库唯一约束是最终幂等防线。
6. 审核通过后打卡状态为 `APPROVED`、任务状态为 `COMPLETED`，并写入完成时间与 `REVIEW_APPROVED` 事件。
7. 任一步写入失败都回滚整个事务，不允许出现任务已完成但积分未到账，或积分到账但任务未完成。

## 3. 数据设计

V24 新增 `growth_point_account` 和 `growth_point_ledger`。所有主键均为 19 位雪花数字；一对一积分账户直接复用学生雪花标识作为账户主键，迁移时为既有学生回填零余额账户，新建学生在创建事务内建立账户。

账户保存 `total_points`、`available_points` 和 `version_no`，余额更新同时校验版本。台账保存学生、账户、来源任务实例、来源类型、来源组织、变更类型、数量、可用积分变化、审核人和发生时间。原台账禁止覆盖，后续纠错通过反向台账关联原记录。

V24 同时扩展打卡状态约束，允许 `APPROVED`；扩展任务事件约束，允许 `REVIEW_APPROVED`。

## 4. 原子事务流程

1. 校验功能开关和业务审核角色。
2. 按任务实例和当前审核人加行锁读取状态、学生、来源和基础积分。
3. 加行锁读取最新 `SUBMITTED` 打卡。
4. 加行锁读取学生积分账户；缺失时以学生标识建立零余额账户后重新锁定。
5. 将打卡更新为 `APPROVED` 并写审核人、审核时间。
6. 以版本条件增加累计积分和可用积分。
7. 写入唯一 `TASK_REWARD` 台账。
8. 将任务从 `PENDING_REVIEW` 更新为 `COMPLETED` 并写完成时间。
9. 写入 `REVIEW_APPROVED` 任务事件并返回本次奖励及新余额。

## 5. API 与前端

新增 `POST /api/v1/task-reviews/{assignmentId}/approve`，请求体为空。成功响应包含任务实例、完成状态、打卡及其通过状态、本次奖励、累计积分、可用积分和台账标识；所有 19 位标识按字符串返回。

Web 审核抽屉展示基础积分，并提供“审核通过并发放积分”按钮。点击后二次确认，成功后关闭抽屉并刷新待办。驳回和转交继续使用 V23 原有流程。小程序不提供审核操作，学生刷新任务详情后可看到 `COMPLETED` 状态；积分账户展示另行进入后续里程碑。

## 6. 异常与安全

非当前审核人和跨范围对象统一返回资源不存在。重复审核、并发旧请求或账户版本变化返回状态冲突。接口不接受客户端积分数量、学生标识、来源类型或账户余额，所有派生值均从锁定后的服务端数据计算。

## 7. 测试与验收

迁移测试验证 V1 至 V24 连续执行、44 张表、非自增雪花主键、账户回填、检查约束和唯一任务奖励。后端端到端测试使用服务端任务基础积分验证账户双余额同步、打卡通过、任务完成、台账和事件完整、重复审核不重复入账、非审核人不可访问；任务定义既有校验继续保证难度 1 至 3 对应 10、20、30 分。Web 测试验证通过按钮、二次确认、接口调用和待办刷新。
