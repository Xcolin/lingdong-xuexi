# 灵动学习 数据库备份与恢复（V1.0）

> 本文档为任务 6.3 交付物：备份恢复脚本使用说明与恢复演练证据。
> 恢复处置原则沿用 BRD 与《部署运维与发布方案》：删除仅解除业务可见关系，物理恢复必须走受控流程；
> **Flyway 失败采用修复迁移（repair + 修正后续迁移脚本），不回滚、不改写已成功执行的历史脚本。**

## 1. 备份范围

| 对象 | 方式 | 说明 |
|---|---|---|
| 数据库 | `tools/db-maintenance.ps1 -Mode backup` | 全表结构与数据快照，AES-256-GCM 整体加密（`database.enc` + `manifest.properties` 含表数/行数/SHA-256） |
| 附件内容 | 文件系统目录备份 | `ATTACHMENT_LOCAL_ROOT`（默认 `data/attachments`）整体纳入备份，与数据库同窗口执行 |
| 应用日志 | 文件系统目录备份 | `logs/`（30 天滚动），事件追溯依据 |

云对象存储暂未接入；附件以本地持久卷为准（见《外置配置与发布检查.md》）。

## 2. 脚本用法（tools/db-maintenance.ps1）

- 备份：`pwsh tools/db-maintenance.ps1 -Mode backup [-BackupDir <目录>]`
- 恢复到隔离库：`pwsh tools/db-maintenance.ps1 -Mode restore -BackupDir <目录> -Schema ld_verify_<8位日期>_<8位十六进制>`
- 源库一致性核对：`-Mode verify-source -BackupDir <目录>`（快照与当前源库逐表 DDL/列/行摘要比对）
- 原库保留数据核对：`-Mode verify-retained -BackupDir <目录>`（备份中每行在当前库逐一存在且字段一致）
- Flyway 只读校验：`-Mode validate -Schema configured|<隔离库> -BackupDir <目录>`。成功判据：最新版本全部成功且失败历史为 0；源码中存在未发布迁移时报 `RESOLVED_VERSIONED_MIGRATION_NOT_APPLIED` 属预期

安全约束：

1. 备份密钥为随机 32 字节，仅经 Windows 当前用户 DPAPI 保护存放（`backup-key.dpapi`），不写入脚本与配置；跨机器/跨用户恢复必须另行受控转移密钥，不能仅复制加密文件就宣称可恢复。
2. 连接凭据从外置配置文件读取，不打印、不落日志；`restore` 只允许 `ld_verify_` 前缀命名的隔离库，禁止直接覆盖业务库。
3. 备份前预检拒绝触发器/存储过程/事件/非 InnoDB 表等不支持对象。

## 4. Flyway 失败处置（修复迁移，不回滚）

1. 迁移失败时**先停止写操作**，以只读方式核对：`SELECT version, success FROM flyway_schema_history ORDER BY installed_rank DESC LIMIT 20` 与失败迁移实际产生的部分对象。
2. 在隔离库用备份恢复后**先重演修复方案**（`-Mode restore` + `-Mode validate`），成功后才允许在业务库执行。
3. 处置方式按优先级：
   - 迁移脚本本身有缺陷：**新增后续版本迁移修正**（如 V56 失败时新增修复版并修正 Mapper，历史 V56 成功记录保持）；若迁移仅部分执行且失败版本从未成功，可在备份核对后由 `flyway repair` 清除失败历史后重跑该版本；
   - 数据不符合迁移前置条件：先受控修正数据，再续跑迁移；
   - **禁止**：改写已成功执行的迁移脚本、手工篡改 `flyway_schema_history.success`、删除业务表回滚。
4. 恢复执行后必须：`-Mode verify-retained` 核对备份中所有原行仍存在且字段一致；`-Mode validate -Schema configured` 校验失败历史为 0。

## 5. 已知限制（不虚构）

- RPO/RTO 目标、备份异地存放、定时调度与监控告警阈值未确认，部署评审时随生产环境一并确定（外部待办）。
- 演练于 Windows 单机执行，DPAPI 密钥保护仅限当前用户；生产环境应改用密钥服务或等价受控方案。
